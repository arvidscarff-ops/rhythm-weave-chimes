# PHASE Product Roadmap

**Document role:** Architecture-aware build sequencing  
**Run:** 7 of the PHASE Project Bible documentation plan  
**Authority:** Strategic sequencing; not a claim about repository implementation  
**Last updated:** 2026-08-02

---

## 1. Roadmap thesis

> **Prove the instrument. Then prove one crossing. Then prove a loop. Then build the foundations that let the loop become a world. Only afterward make that world broad, persistent, and social.**

PHASE’s largest risk is not lack of features. It is building a wide world before proving that a long audiovisual transit is compelling.

The roadmap therefore proceeds in concentric rings:

1. establish the actual codebase baseline;
2. preserve the originating Trigger Engine reference and reset the experimental product shell;
3. protect timing invariants;
4. prove an exceptional standalone generative audiovisual instrument;
5. prove one exceptional crossing;
6. prove that several crossings form a game loop;
7. make content and state scalable;
8. introduce authoritative world weather;
9. deepen progression, narrative, and persistence;
10. add community systems that preserve solitude;
11. expand content only after the production pipeline works.

## 2. Evidence boundary and current state

### 2.1 What is confirmed

- PHASE exists as a Lovable-created application.
- The project is connected to a private GitHub repository.
- The repository has been cloned/opened for Codex work.
- Lovable and GitHub are intended to remain connected.
- The target product, game systems, lore, timing invariants, and visual direction are now documented through Runs 1–6.

### 2.2 What is not confirmed

This documentation run has not inspected the PHASE repository.

Therefore the roadmap must not claim:

- which features currently work;
- which architecture already matches the target;
- current framework details;
- current database schema;
- authentication status;
- current Trigger Engine implementation;
- whether collisions trigger notes;
- whether Phase Zero is implemented;
- what “My Studio” currently contains;
- current test/build health;
- specific technical debt;
- current performance on long sessions.

### 2.3 First engineering action

Before implementation, Codex must perform a read-only codebase audit.

The audit must separate:

1. confirmed implementation findings;
2. conflicts with the documented target;
3. risks and bottlenecks;
4. recommendations;
5. parts already well designed and worth preserving.

The audit must not modify source code.

## 3. Roadmap principles

1. **One crossing before one world.**
2. **Musical authority before environmental modulation.**
3. **Formal closure before weather-driven duration.**
4. **Data-driven content before content scale.**
5. **World authority before shared persistence.**
6. **Meaningful progression before currencies.**
7. **Asynchronous connection before synchronous social systems.**
8. **Moderation before public communication.**
9. **Realtime proof before asset-production scale.**
10. **Documentation status before implementation assumption.**
11. **Measure experiential quality, not only engagement.**
12. **Do not build maximum vision systems to compensate for a weak crossing.**

## Phase R — Reset / PHASE 2.0

**Goal:** Turn the experimental Lovable prototype into a clean instrument-first foundation without discarding valuable engine, Studio, visual, data, or backend work.
**Dependency:** Phase A audit and the selected Lucid Rhythms reference corpus.
**Scope:** Documentation, salvage, product-shell reset, foundational implementation, and authoring-tool consolidation.

### R0 — Reference and Reset charter

- preserve Lucid Rhythms as the originating Trigger Engine reference;
- record the six selected works;
- distinguish observation, inference, capability target, and prohibited copying;
- record the standalone instrument as PHASE’s gateway;
- define Reset scope and approval boundaries.

### R1 — Salvage map

Classify every active product surface and supporting system as:

- preserve unchanged;
- preserve and refactor;
- replace;
- retain temporarily as reference;
- remove only after replacement verification.

Inventory:

- routes and screens;
- timing/audio/scene code;
- Trigger Engines;
- My Studio;
- Supabase schema, storage, functions, and policies;
- generated assets and visual experiments;
- data requiring backup;
- current behavior requiring screenshot or fixture preservation.

No deletion occurs during the salvage-map task.

### R2 — Clean entry shell

- create an immediate instrument-first entry experience;
- keep controls minimal, legible, and suitable for long sessions;
- retain access to private My Studio;
- avoid premature account, map, progression, lore-dashboard, and game-menu requirements;
- introduce world evidence gradually rather than through exposition;
- keep old product surfaces until replacement scope is approved.

### R3 — Authoritative Trigger Engine core

- establish the musical/event foundation described in Phase B;
- prove one correct reference event path;
- preserve useful normalized-phase mathematics;
- build lifecycle, determinism, diagnostics, and tests;
- keep rendering subordinate to musical truth.

### R4 — Initial Trigger Engine family

Deliver a small set of materially distinct reference engines rather than carrying every experiment forward immediately.

Initial families may include:

- pendulum/wave;
- orbital/radial;
- linear/lattice/path.

Exact choices follow detailed reference annotation and project-owner approval. Variants must differ structurally, not only through color, particle count, or sound pack.

### R5 — Private My Studio

Consolidate the existing Studio into a reliable owner/developer authoring environment for:

- sound packs and samples;
- tuning, scales, and progressions;
- compositions and voices;
- Trigger Engine and scene configuration;
- authoritative preview;
- validation;
- versioning and publication;
- backup/export;
- safe authentication and storage.

Player-facing authoring remains unresolved and out of Reset scope.

### R6 — Superseded-code removal

Remove obsolete UI, duplicated engine paths, dead components, redirects, debug surfaces, styles, and assets only after:

- replacement behavior is verified;
- data is protected;
- a complete removal manifest and diff are reviewed;
- project-owner approval is explicit.

### R7 — Game-graphics laboratory

After the instrument and Studio foundation is stable, test:

- Canvas 2D limits;
- WebGL and shader workflows;
- procedural sky, cloud, fog, light, trail, and particle systems;
- 2D, 2.5D, and restrained 3D approaches;
- cockpit framing;
- open-source/licensed asset pipelines;
- reduced motion;
- long-session performance.

Select the rendering stack from prototypes, visual review, production feasibility, and measurement. Do not select it merely because it is conventionally associated with games.

### Reset exit criteria

- the selected reference and originality boundary are documented;
- the active product opens into a compelling standalone audiovisual instrument;
- a small Trigger Engine family shares one correct architecture;
- My Studio reliably authors and previews the supported content;
- valuable prototype work is preserved or deliberately migrated;
- superseded code is removed only through an approved manifest;
- long-session, lifecycle, accessibility, and security baselines pass;
- the project is ready to situate the instrument inside one crossing.

### Do not build during Reset

- final world map;
- large route network;
- progression trees or currencies;
- authoritative living weather;
- multiplayer/community;
- player-authored Trigger Engines;
- final game-graphics stack without prototypes;
- marketing automation.

## 6. Phase B — Freeze and test the musical foundation

**Goal:** Make the audiovisual timing contract explicit and executable.  
**Dependency:** Phase A audit and Phase R Reset charter/salvage map.
**Why now:** Every future transit, weather, progression, and visual system depends on it.

### Work

- select/document canonical time representation;
- establish one logical rhythm authority;
- centralize scale/tuning reference;
- formalize voice and macro-cycle data;
- define exact Phase Zero semantics;
- remove collision-derived authoritative notes if found;
- decouple musical events from render frequency;
- add deterministic event identities;
- add pause/resume/remount reconstruction;
- build diagnostics;
- build unit/property/simulation tests.

### Required tests

- closure across all canonical voice sets;
- exact Phase Zero;
- frame-rate independence;
- no duplicate/missed events;
- long-session drift;
- hidden-tab/background recovery;
- Trigger Engine remount;
- identical seeded input;
- audio/visual event alignment.

### Exit criteria

- the compact implementation contract in `AUDIO_RHYTHM_ARCHITECTURE.md` is true;
- timing invariants are protected by tests;
- current Trigger Engine behavior can be inspected through diagnostics;
- configuration changes follow a declared quantization policy.

### Do not build yet

- weather-driven tempo;
- global simulation;
- user-created Trigger Engines;
- large progression trees;
- route fleet.

## 7. Phase C — Prove one crossing

**Goal:** Demonstrate that one 10–20 minute transit is worth inhabiting.  
**Dependency:** Stable musical foundation.

### Scope

- one origin;
- one destination;
- one route;
- one glider/cockpit context;
- one Trigger Engine/composition;
- one sound world and scale;
- route progress;
- one environmental/weather preset;
- one sky/environment;
- a small transmission library;
- departure;
- arrival;
- focused and peripheral-attention behavior.

### Visual proof

- stable long-duration sky;
- recognizable PHASE atmosphere;
- cockpit framing;
- rhythmic geometry;
- calm state hierarchy;
- daylight beauty;
- one controlled sign of unease;
- reduced-motion mode.

### Narrative proof

- routine operational transmissions;
- human context;
- one unusual transmission;
- no lore dump.

### Evaluation questions

- Does the composition remain musically interesting?
- Can the player look away safely?
- Is route progress legible?
- Does the world feel larger than the route?
- Does arrival feel earned?
- Does the player want another crossing?
- Is performance stable for the full duration?

### Exit criteria

- representative users complete the crossing;
- foreground and background use both function;
- no obvious short loop;
- audiovisual alignment remains credible;
- arrival provides formal/emotional closure;
- the team chooses to make a second route because the first works, not because more content might hide weakness.

### Required systems

- route availability;
- heard/unheard transmission state;
- first-pass Navigator/glider progression;
- content versioning;
- telemetry;
- accessibility;
- authoring workflow.

### Product tests

- first-transit completion;
- second-transit start;
- return after several days;
- account creation after value is demonstrated;

### Exit criteria

- adding a route is primarily content configuration, not duplicated application logic;
- progression deepens perception rather than only numbers;
- the map produces meaningful choice;
- the slice supports several hours without collapsing into repetition;
- the first chapter has a clear emotional arc.

## 10. Phase F — Authoritative living weather

**Goal:** Give the world independent, shared atmospheric state.  
**Dependency:** Timing foundation, route graph, persistence, data-driven content.

### Initial variables

Start small:

- wind;
- precipitation;
- visibility;
- harmonic stability;
- anomaly pressure.

These are planning candidates, not locked canon.

### World simulation

- one authoritative world clock;
- region graph;
- condition transitions/fronts;
- route modifiers;
- forecast generation;
- uncertainty;
- snapshots/history;
- scheduled updates;
- client retrieval/cache.

### Route integration

- openings/closures;
- expected duration;
- risk/advisories;
- visual parameters;
- approved musical modulation.

### Audio integration

Before implementation, choose one documented weather-to-composition model:

- cycle count;
- global time scaling;
- quantized tempo states;
- orchestration/density;
- hierarchical formal mapping.

Weather must not directly mutate Trigger Engine clocks.

### Exit criteria

- all players receive consistent gameplay-relevant conditions;
- forecasts are useful but not perfectly deterministic;
- route closures have understandable causes;
- visual/audio state agrees with forecast;
- background/offline passage of weather works;
- musical closure remains exact.

- reporting;

- rate limits;
- privacy;

- connection does not destroy solitude;
- users can fully opt out;

## 17. Decision gates

### Gate 1 — Musical foundation

Proceed only if:

- central authority is confirmed;
- closure tests pass;
- long-session drift is acceptable;
- visuals/audio share event identity.

### Gate 2 — One crossing

Proceed only if:

- representative users complete it;
- it works actively and peripherally;
- performance is stable;
- users want another.

### Gate 3 — Vertical slice

Proceed only if:

- multiple routes feel distinct;
- content is data-driven;
- progression strengthens the experience;
- onboarding/account flow works.

### Gate 4 — Living world

Proceed only if:

- server authority and route graph exist;
- weather mapping is decided;
- forecasts produce meaningful planning.

### Gate 5 — Community

Proceed only if:

- privacy/moderation are staffed;
- asynchronous systems demonstrate value;
- social features preserve solitude.

## 18. Risk register

| Risk | Consequence | Mitigation |
|---|---|---|
| Weak long-form crossing | Entire product thesis fails | Prove one crossing before scope |
